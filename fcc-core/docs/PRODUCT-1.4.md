# FCC 通用自主反馈产品 · 架构、用户合同与分阶段实现

## 需求判断

用户提出「基座 → 向用户索要信息 → 量化套入控制理论 → 运行 → 节点反馈 → 逐步改善」的方向正确，但原先的“目标/输入/频率”**只能确定观察系统，不能确定控制系统**。要从监控走向闭环，还必须获得真实可控变量、行动映射与权限、响应延迟、代价、副作用及独立验证标准。

不应该把一个自然语言目标伪装为状态空间模型，更不能把没有业务权限的 AI 输出直接执行。推荐架构是：

`Agent SKILL（对话采集） → Intake & Commissioning（模型校验与分层确认） → FCC Core（数学与确定性引擎） → Observation adapters / Actuator adapters（真实数据/动作） → Verification（后验数据） → Inbox / Approved notifier（节点报告） → 受监督策略变更`。

## 用户需要输入哪些信息？

| 层 | 必填的最少信息 | 进一步可选 | 目的 |
|---|---|---|---|
| **Outcome 最终结果** | 要改善的结果 | 期限、优先级 | 不把度量当成业务目标 |
| **Measure 可观测** | 指标名、目标值、至少/至多/接近、来源 | 单位、容差、原始基线、测量误差、验证人 | 计算误差，防止假数字 |
| **Input 数据入口** | 数据多久产生、如何进入系统 | 异常值、缺失策略、日志/API/设备适配器 | 维持真实输入流 |
| **Controller 可控制** | 仅观察/建议/需批准 | 可控手段、接口、额度、单次幅度、后果可逆性 | 确定是否真能闭环执行 |
| **Clock 多时间尺度** | 采样、评估、节点报告 | 干预间隔、响应等待、验证延迟、长期复盘 | 防止过密反馈、错误归因 |
| **Guard & Success** | 默认连续 3 次目标命中 | 潜在副作用、预算、回滚、真实业务成功定义 | 避免以牺牲其他目标换取单指标好看 |

**建议对普通人只分五屏提问，复杂参数仅在适当时候追问**。当他只想监测时不该强迫填写完整 MPC 矩阵。只有当尝试真实控制、数学反馈或存在明显不确定性时，再进一步追问动态模型、因果杠杆、控制方向、控制增益/约束、模型可识别性。

## 产品状态机

概念上：

`草案 → 量化核验 → 等待数据接入 → 运行中 → 节点评估 → 候选调整 → 人工批准并实际执行 → 等待系统响应 → 后验观察 → 审慎策略升级 / 暂停 / 恢复`。

实现于 1.4 的：持久化草案、缺项追问、配置编译、启动监测、周期评价、持久化检查点收件箱、记录候选/外部执行确认/前后观察验证、暂停恢复。**未实现**：跨 AI 平台原生主动推送、自动系统参数调整、完整因果分析、多变量自动整定、真实设备安全认证、分布式 HA。用户应明确知道哪一层已上线。

## 四个时钟不可合并

- 采样：决定多久拿到一条新观测。
- 评估：决定多久比较目标和当前观测；在 1.4 内一般不快于采样。
- 验证：干预产生后至少等到响应时间，且必须获得执行后的独立观测。
- 报告：多久向本地收件箱生成决策节点；报告频率可以远低于采样频率。

长期的模型再辨识/参数调优可以是第五个独立时钟，但此版本尚未自动执行。

## 结果解释规则

- 目标是「至少 100」，读数 105：**达成阈值**，不是偏差 -5 或超调警告；仍需连续新数据验证稳定性。
- 目标是「至多 10」，读数 7：阈值达成；不能要求强行拉回 10。
- 目标是「接近 100 ± 5」，读数 85：偏差 +15，尚未达标。
- 目标是「更健康/更好/更满意」但没有被认同的可验证指标：继续问目标如何核实，先停留在人工审查/观察。
- 只有 AI 推断的数据：可能形成待核实线索，但不能单独标记客观结果已经实现。
- 有改善记录但没有同时期其他变量控制：**前后关联**，不应宣称行动必然导致改善。
- 没有新的观测：提示数据过期，不要对同一旧数据反复生成“越来越好”的判断。

## API 输入 / 输出示例（仅通用的虚构指标）

```json
{
 "title":"通用目标A",
 "desired_outcome":"让指标在规定资源内满足标准",
 "metric_name":"指标A", "unit":"U", "target_mode":"at_least",
 "target_value":100, "tolerance":2,
 "data_source":"human_input", "data_delivery":"manual",
 "sampling_seconds":3600,"evaluation_seconds":3600,
 "report_seconds":86400,"sustained_samples":3,
 "action_authority":"suggest","controllable_levers":[],
 "constraints":["不得执行未批准动作"]
}
```

`POST /api/onboarding/plans` 返回 `plan_id`、`next_questions` 和 `required_missing`；用户确认后 `GET /api/onboarding/plans/{id}/compile` 检查编译结果，`POST /.../activate` 获得真正的 `loop_id`。后续提交 `POST /.../observations`，读取 `GET /.../status` 和 `/outbox`。

干预试验的状态是 `proposed → applied_pending_verification → verified_observational`。外部执行证据是用户陈述/日志来源记录，并不是控制软件自身自动执行的证明。过程不会自动创建物理动作。

## 未来扩展优先级

P1：真实数据连接器、采集异常告警、受认证的外部主动报告通知及用户审批收件箱。

P2：完整执行器协议（动作范围、执行回读、幂等、回滚）、规则映射 DSL、优化动作的因果检验和对照实验；再按系统建模质量自动选择合适控制器。

P3：多目标/多变量和约束优化、可观察性/可控性自动预检、更完善系统辨识、长期性能漂移、回归测试与受审核策略升级。

**不能保证所有环境最终一定达到目标**。还需要目标本身可行、可控动作足够有效、观测真实且延迟有限、无无法控制的外部扰动，控制权限可靠。
